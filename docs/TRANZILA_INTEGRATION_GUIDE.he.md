# הכנה לחיבור טרנזילה: כסף אמיתי, קויינס ומנויים

נבדק מול התיעוד הרשמי של טרנזילה בתאריך **11 בספטמבר 2026**.

מטרת המסמך היא להכין חיבור לסליקה ולמעקב בממשק הניהול. זהו מסמך תכנון; יצירת בקשת רכישה במערכת אינה חיוב ואינה הוכחת תשלום. אין במסמך פרטי מסוף או מפתחות אמיתיים. עובדות על הספק מצוטטות בקישורים רשמיים; כללי המערכת המוצעים מסומנים כהמלצות שלנו.

## 1. מה טרנזילה מציעה ומה מתאים כאן

| יכולת | שימוש אצלנו | מקור רשמי |
|---|---|---|
| DirectNG iFrame | עמוד תשלום מאוחסן לרכישת חבילת קויינס | [DirectNG](https://docs.tranzila.com/docs/payments-and-billing/iframe-integration-directng) |
| Hosted Fields | שדות תשלום מאוחסנים בעיצוב מותאם, אם נדרש בהמשך | [Hosted Fields](https://docs.tranzila.com/docs/payments-and-billing/hosted-fields) |
| Handshake V2 | נעילת סכום העסקה בצד הספק לפני פתיחת התשלום | [Handshake V2](https://docs.tranzila.com/docs/payments-and-billing/handshake-v2) |
| My Billing / STO V2 | הקמה וניהול של חיובים מחזוריים למנוי | [STO V2](https://docs.tranzila.com/docs/payments-and-billing/sto-api-v2) |
| עסקאות אשראי ב־API | חיוב, זיכוי וביטול על פי סוג העסקה | [Transactions API](https://docs.tranzila.com/docs/payments-and-billing/tranzila-transactions-api-1/create-a-credit-card-transaction) |
| Reports API | התאמת הרישומים המקומיים לעסקאות אצל הספק | [דוחות עסקאות](https://docs.tranzila.com/docs/reports/tranzila-transaction-reports-api/gettransactions) |
| חשבוניות ומסמכי זיכוי | קישור מסמך חשבונאי לעסקה | [Invoices API](https://docs.tranzila.com/docs/invoices/invoices-api/create-document) |
| קישור לתשלום | חלופה עתידית למשלוח דרישת תשלום ללקוח | [דרישות תשלום](https://www.tranzila.com/דרישת-תשלום/) |

**המלצת יישום:** להתחיל ב־DirectNG עם Handshake עבור קויינס, ובמסלול My Billing מאושר לחשבון עבור מנויים. לשמור מתאם ספק נפרד, כדי שמודלי הארנק וההרשאות לא יהיו תלויים בפורמט טרנזילה.

בתיעוד הראשי קיימים גם Bit, Apple Pay, 3DS ומס״ב. עצם הופעת שירות בתיעוד אינה אישור שהוא מופעל במסוף שלנו. [מפת השירותים](https://docs.tranzila.com/)

## 2. מה צריך לקבל ולהגדיר אצל טרנזילה

- מסוף פעיל ושם המסוף, גישה לממשק הניהול והרשמה לשירותי API לקבלת application key ו־secret. סודות נשמרים בשרת בלבד. [Authentication](https://docs.tranzila.com/docs/payments-and-billing/authentication)
- עבור Handshake V2 נדרש מודול Token בתשלום. ב־iFrame צריך להפעיל Handshake בהגדרות המסוף; לאחר ההפעלה עסקאות ללא `thtk` תקף יידחו. התוקף המתועד הוא 20 דקות. [Handshake V2](https://docs.tranzila.com/docs/payments-and-billing/handshake-v2)
- למנויים נדרש My Billing בתשלום. יש ליצור טוקן דרך iFrame או Hosted Fields ולוודא איזה מסוף מוגדר למודול; לרוב זהו מסוף TOK. [יצירת STO](https://docs.tranzila.com/docs/payments-and-billing/sto-api-v2/createstov2)
- כתובות HTTPS ציבוריות ומוגדרות מראש לחזרת לקוח ולהודעות שרת. ב־DirectNG הפרמטרים הם `success_url_address`, `fail_url_address`, `notify_url_address`. אלו שלושה תפקידים שונים. [DirectNG](https://docs.tranzila.com/docs/payments-and-billing/iframe-integration-directng)
- יש לתאם שדות מזהים במסוף: מזהה הזמנה מקומי, מזהה לקוח פנימי וסוג מוצר. בתיעוד עסקאות האשראי מוסבר ש־`user_defined_fields` דורש הגדרה במסוף, בעוד `client` אינו מציג את הפרטים ברשומת העסקה או בדוחות. [שדות לקוח בעסקה](https://docs.tranzila.com/docs/payments-and-billing/tranzila-transactions-api-1/create-a-credit-card-transaction)

**פרטים שחייבים לקבל עבור החשבון שלנו, ולא הוכחו בבדיקה זו:** מסוף בדיקה והוראותיו; מטבעות ושיטות תשלום מאושרים; הרשאות API ודוחות; מסוף TOK וקישורו למסוף הראשי; הרשאות החזרים; כתובות API המאושרות למסוף; תמחור המודולים; הפעלת 3DS; תהליך אימות הודעות שרת; תנאי תפעול, מגבלות קצב ושחזור הודעות. צריך לתאר לטרנזילה במפורש שמוכרים מנויים וקויינס למשחק, ולברר התאמה לתנאי המסוף, במיוחד אם קיימת או מתוכננת אפשרות פדיון.

## 3. אימות API והתנהגות נכונה

ה־API משתמש בארבע כותרות: `X-tranzila-api-app-key`, `X-tranzila-api-request-time`, `X-tranzila-api-nonce`, `X-tranzila-api-access-token`. הזמן הוא Unix UTC בשניות; ה־nonce מופק מ־40 בתים אקראיים. בדוגמה הרשמית הוא מקודד ל־80 תווי hex. הטוקן הוא HMAC-SHA256, כאשר ההודעה היא ה־app key והמפתח הוא שרשור secret, זמן ו־nonce. [Authentication](https://docs.tranzila.com/docs/payments-and-billing/authentication)

דוגמה מקומית לחישוב בלבד, בהתאם לאלגוריתם המתועד:

```python
import hashlib
import hmac
import secrets
import time

request_time = str(int(time.time()))
nonce = secrets.token_hex(40)
access_token = hmac.new(
    (secret + request_time + nonce).encode("utf-8"),
    app_key.encode("utf-8"),
    hashlib.sha256,
).hexdigest()
```

**המלצות המימוש שלנו:**

- לא לחשוף secret, סיסמת מסוף או טוקן כרטיס ל־frontend, ללוגים או לדף הניהול. אימות TLS חייב להישאר פעיל, גם אם דוגמת ספק מסוימת מבטלת אותו.
- להגביל יעד קריאות לרשימת כתובות ספק קבועה; כתובת חזרה לא מתקבלת באופן חופשי ממשתמש.
- להגדיר timeouts, מגבלת גודל תגובה, טיפול בשגיאות ופענוח קשיח. timeout אחרי שליחת חיוב הוא תוצאה לא ידועה: לברר את העסקה לפני ניסיון נוסף.
- nonce חדש מאמת בקשה חדשה; הוא אינו תחליף למפתח idempotency עסקי שלנו. מפתח מקומי קבוע לכל ניסיון רכישה, אילוץ ייחודיות ונעילת DB ימנעו הכפלת עסקה/הענקה.
- לבדוק HTTP, קוד יישומי, קוד סליקה, מזהה עסקה, סכום, מטבע ומסוף. ביצירת STO מתועד ש־HTTP 200 עלול להכיל שגיאה יישומית; קבלת `sto_id` אינה הוכחת חיוב. [תשובות STO](https://docs.tranzila.com/docs/payments-and-billing/sto-api-v2/createstov2)

DirectNG מציע גם `DCdisable` למניעת חיוב חוזר ודורש הגדרת שדה 20 במסוף. יש לבדוק הפעלה בפועל ולא להניח שהפרמטר לבדו מספק הגנה. [מניעת כפילות](https://docs.tranzila.com/docs/payments-and-billing/iframe-integration-directng)

## 4. הפרדה בין כסף אמיתי לקויינס

**המלצת מודל עסקי:**

| נתון | משמעות | אחסון וחישוב |
|---|---|---|
| סכום תשלום | כסף שנגבה אצל ספק הסליקה | `Decimal` ומטבע מפורש, או יחידות משנה שלמות |
| כמות קויינס | יחידות משחק שנרכשו/הוענקו | מספר שלם ביומן ארנק נפרד |
| מסלול מנוי | הרשאת שימוש לתקופה מוגדרת | מסלול, תאריך התחלה וסיום, סטטוס וחיובי התקופות |
| החזר כספי | תנועה נגדית לתשלום מסוים | סכום, מטבע וקישור לעסקת המקור |
| ביטול קויינס | תיקון ביחידות המשחק | תנועה נגדית מתועדת, ללא מחיקת היסטוריה |

למשל, רכישת **1,000 קויינס במחיר 20.00 ILS** היא הכנסה של 20.00 ILS והענקה של 1,000 יחידות משחק. לא מחברים בין המספרים ולא מציגים את הקויינס כיתרת שקלים. הטבה חינמית או הענקת אדמין אינה הכנסה.

מחיר, מטבע, כמות קויינס ומסלול חייבים להיגזר מקטלוג מאומת בשרת ולהישמר כתמונת מצב בהזמנה. אין לחשב זכאות לפי סכום שהגיע מהדפדפן. הפורמטים משתנים בין הממשקים: ב־iFrame שקלים מיוצגים כ־`currency=1`; ב־STO וב־API קיימים שדות מטבע אחרים. יש לבצע מיפוי מפורש לכל endpoint. [מטבעות iFrame](https://docs.tranzila.com/docs/payments-and-billing/iframe-integration), [STO](https://docs.tranzila.com/docs/payments-and-billing/sto-api-v2/createstov2)

## 5. זרימת רכישת קויינס המוצעת

1. השרת מאמת משתמש ומוצר, מקבע מחיר וכמות ויוצר בקשה עם מזהה ייחודי. בקשת אדמין מתעדת גם את האדמין וגם את הלקוח.
2. מתאם טרנזילה מבקש Handshake מהשרת ומכין תשלום מאוחסן בהתאם לחוזה המסוף.
3. המשתמש משלים תשלום אצל טרנזילה. עמוד החזרה מציג מצב ממתין עד שהשרת אישר את העסקה.
4. השרת מקבל הודעה, מזהה את העסקה ומאמת אותה מול מקור ספק מוסמך לפי הסעיף הבא.
5. בתוך טרנזקציית DB אחת נרשמים תשלום מאומת, תנועת ארנק והענקה חד־פעמית. מפתח ההענקה קשור לעסקת התשלום.
6. אם ההענקה נכשלה לאחר שהתשלום אושר, משחזרים את ההענקה מהתשלום הקיים; לא מחייבים שוב.

## 6. Notify / webhook: מה מאומת ומה עדיין חסר

ב־My Billing קיימות הודעות POST לכל עסקת STO; הכתובת מוגדרת ב־Settings → Terminal → My-Billing. בין השדות המתועדים: `sum`, `currency`, `Response`, `ConfirmationCode`, `TranzilaTK`, `index`. קוד `Response=000` מציין הצלחה בפורמט זה. [התראות My Billing](https://docs.tranzila.com/docs/payments-and-billing/sto-api-v2)

**פער מתועד בבדיקה שלנו:** בדפי Notify ו־STO שנבדקו לא נמצא חוזה מלא לחתימת הודעה נכנסת, כותרת חתימה, canonicalization, תוקף זמן, retry/ACK או סדר משלוח. כותרות HMAC של קריאות ה־API היוצאות אינן הוכחה שה־webhook הנכנס חתום באותו אופן. אין להמציא כותרת `X-Tranzila-Signature` או להתייחס לסוד מקומי כיכולת רשמית. [Notify](https://docs.tranzila.com/docs/vibe-coding/closing-an-order-in-base44-using-notify-page), [STO](https://docs.tranzila.com/docs/payments-and-billing/sto-api-v2)

**המלצות מחייבות למימוש שלנו לפני הפעלת הענקה אוטומטית:**

- לקבל מהספק חוזה אימות מוסכם ולבדוק אותו, או לבצע בדיקת עסקה ב־API מאומת לפי מזהה עסקה לפני הענקה. לחבר ללקוח ולבקשה דרך מזהה הזמנה מאומת, לא לפי סכום וזמן בלבד.
- API רשמי לשליפת עסקה הוא `POST https://api.tranzila.com/v1/transactions`, עם מסוף ו־`transaction_index`, וכותרות אימות. יש לוודא הרשאה, מבנה תגובה וזמן זמינות הנתונים במסוף הבדיקה. [שליפת עסקה](https://docs.tranzila.com/docs/reports/track-transaction-data/get-transaction-information)
- הודעה שאינה ניתנת לאימות תירשם כהמתנה לבירור, בלי קויינס או הפעלת מנוי. הצלחה בדפדפן, מקור IP בלבד או `Response=000` בבקשה ציבורית אינם הוכחת תשלום.
- לזהות כפילות לפי ספק, סביבה, מסוף ומזהה עסקה; לא להניח שמזהה מספרי ייחודי בין מסופים.
- לשמור מידע מצומצם ביומן: מזהה, סוג, שעה, סטטוס עיבוד וקוד שגיאה. לא לשמור payload מלא שעלול להכיל פרטי לקוח או טוקנים.
- לבדוק הודעות חוזרות, מקבילות, חסרות ומאוחרות; אין לאפשר לכישלון ישן להוריד תשלום מאומת לסטטוס נכשל.

## 7. מנויים וחיובים חוזרים

`POST https://api.tranzila.com/v2/sto/create` מקים הוראת חיוב; בין תדירויותיו שבועית, חודשית, רבעונית, חצי־שנתית ושנתית. יש לקבוע את תאריך החיוב הראשון, מספר החיובים והתדירות לפי המוצר. יש לאשר מול הספק כיצד מייצגים מנוי ללא מועד סיום; לא להעתיק משמעות של פרמטרי iFrame ל־STO V2. [יצירת STO](https://docs.tranzila.com/docs/payments-and-billing/sto-api-v2/createstov2)

My Billing מציע הודעות דוא״ל אוטומטיות לעדכון כרטיס במקרה של כשלים מסוימים וניסיונות חיוב חוזרים לאחר עדכון. לפי התיעוד, התכונה מופעלת כברירת מחדל למנויי המודול וניתנת לכיבוי. יש לבדוק את ההגדרה לפני הפעלה כדי לתאם אותה עם הודעות המערכת שלנו. [התראות ותיקון טוקן](https://docs.tranzila.com/docs/payments-and-billing/sto-api-v2)

**המלצות מערכת:** כל תקופת חיוב מקבלת תשלום נפרד. הפעלה/הארכה מתבצעות רק לאחר תשלום מאומת. כשל חיוב אינו מוחק תקופה שכבר שולמה; מגדירים מראש תקופת חסד. בקשת ביטול, עצירת חיובים אצל הספק ופקיעת הרשאת המנוי הן פעולות שונות. לפני חיבור יש לאמת את API הביטול/עדכון והעיתוי שהמסוף תומך בהם. אין להמיר אוטומטית מנוי PayPal קיים לטרנזילה או לחייב אותו בשני ספקים.

## 8. החזרים ומסמכים

בתיעוד אשראי מופיעים `credit` לזיכוי, `cancel` לביטול ו־`reversal` לשחרור מסגרת J5; פעולות אלו אינן זהות. יש להיצמד לאסמכתת המקור ולשדות endpoint המסוים. [סוגי עסקאות](https://docs.tranzila.com/docs/payments-and-billing/tranzila-api/create-a-credit-card-transaction)

ל־Bit יש endpoint נפרד, `POST https://api.tranzila.com/v1/transaction/bit/refund`, עם מסוף, מזהה עסקה וסכום; מתועדות גם שגיאות כגון החזר שכבר בוצע או סכום גבוה מהעסקה המקורית. אין להשתמש בו עבור אשראי. [Bit Refund](https://docs.tranzila.com/docs/payments-and-billing/bit-api/bit-refund)

**המלצות מערכת:** לא למחוק תשלום; לשמור תנועת החזר מקושרת ומבוקרת. סכום ההחזרים המצטבר לא יעלה על הסכום ששולם. אין לסמן החזר כמושלם בגלל לחיצת אדמין או timeout. צריך להחליט מראש מה עושים בקויינס שכבר נוצלו ובמנוי שכבר התחיל, ולשמור פעולה מתקנת נפרדת. בקשת ביטול מנוי אינה בקשת החזר.

Invoices API מאפשר קישור באמצעות `txnindex` ומסמכים קשורים; יש לקשר את מסמך הזיכוי לתשלום המקורי. מסמך sandbox פנימי אינו חשבונית מס. סוגי המסמכים והגדרות העסק ייקבעו במסגרת הפעלת מודול החשבוניות. [מסמכים](https://docs.tranzila.com/docs/invoices/invoices-api/create-document), [טבלת פרמטרים](https://docs.tranzila.com/docs/invoices/params-table)

## 9. דף מעקב בממשק הניהול

**מפרט מומלץ להמשך חיבור הספק:**

- לכל רכישה: לקוח, מי יצר, סוג מוצר, מסלול/כמות, כסף ומטבע, ספק, סביבה, סטטוס, זמני יצירה/חיוב, מזהי הזמנה ועסקה.
- יומן אירועים: יצירה, שליחה לספק, הצלחה/כשל, הודעה נכנסת, אימות, הענקת קויינס, הפעלת מנוי, בקשת החזר והשלמתו.
- סיכומים נפרדים לכל מטבע וסביבה: סכום ששולם, הוחזר ונטו; בקשות ממתינות אינן הכנסה. קויינס נרכשו/הוענקו מוצגים ביחידות משחק בלבד.
- הפרדה בין ״תשלום שאושר״ ל״כסף שהופקד בבנק״. שליפת עסקאות לבדה אינה הוכחת התחשבנות בנקאית; נתון הפקדות דורש מקור התחשבנות מאומת נוסף.
- סינון לפי תאריך, לקוח, אדמין, מוצר, סטטוס וספק, עם הרשאת כספים ייעודית. אין להציג טוקנים/סודות או payload גולמי.

לדוחות הספק endpoint רשמי `POST https://report.tranzila.com/v1/transaction`, התומך בשליפה לפי מזהה עסקה או טווח תאריכים, דפדוף ופירוט מוצרים. יש להשלים את אימות הגישה עבור החשבון לפני שימוש. **המלצתנו:** ריצת התאמה מחזורית תזהה עסקאות בלי הזמנה, הודעות חסרות והחזרים שבוצעו ידנית אצל הספק. [Transaction Reports](https://docs.tranzila.com/docs/reports/tranzila-transaction-reports-api/gettransactions)

## 10. בדיקות לפני חיוב אמיתי

אין להניח שקיים URL sandbox אחיד או שהשם `sandbox` בקוד מבטיח שאין חיוב. בתיעוד Hosted Fields מופיע שימוש ב־`sandbox: false`; יש לקבל הוראות מסוף בדיקה מפורשות. אותו תיעוד מפרסם תרחישי 3DS לבדיקה. [Hosted Fields](https://docs.tranzila.com/docs/payments-and-billing/hosted-fields)

Apple Pay מתועד ללא סביבת sandbox, עם דרישות HTTPS ורישום דומיין ותהליך בדיקה בסביבת production. יש לתאם בדיקה ייעודית לפני הוספתו, ולא להפעיל חיוב אמיתי אוטומטית במסגרת בדיקות פיתוח. [Apple Pay](https://docs.tranzila.com/docs/payments-and-billing/apple-pay-iframe)

**רשימת קבלה שלנו:**

- הצלחה, סירוב, סגירת דפדפן, תפוגת Handshake, 3DS שנכשל ו־timeout בתוצאה לא ידועה.
- שינוי מחיר/מטבע/כמות מהדפדפן והודעת הצלחה מזויפת אינם מעניקים זכאות.
- שני קליקים ושתי הודעות מקבילות מעניקים פעם אחת בלבד.
- הודעה חסרה משוחזרת בהתאמת דוחות; replay מאוחר אינו משנה תוצאה סופית בצורה שגויה.
- מנוי: חיוב ראשון, חידוש, כשל, עדכון כרטיס, ביטול וחידוש שנכנס במקביל לביטול.
- החזר מלא וחלקי, בקשת החזר כפולה והחזר אחרי ניצול קויינס.
- סכומי הדוחות תואמים לספק, ו־sandbox מופרד מ־live בכל הרשומות והסיכומים.
- לוגים, ממשק הניהול וגיבויים אינם מכילים סודות או פרטי כרטיס מלאים.

## 11. מצב ההכנה בפרויקט והשלבים שנותרו

בעת כתיבת המסמך קיימים ב־`tournaments/billing/models.py` מודלי `CheckoutRequest` ו־`CheckoutEvent`, עם סכום ומטבע נפרדים מכמות קויינס ומסלול מנוי. ההכנה מבוססת בקשות טיוטה; אין להסיק מכך שקיים כבר חיוב טרנזילה פעיל. מודלי התשלומים/המנויים הקיימים כוללים גם תהליך PayPal sandbox, ויש להתאים את זהות הספק והסביבה לפני שימוש משותף בייצור.

עדכון מימוש: נוסף קטלוג ניתן לעריכה, מתאם Handshake/DirectNG ודוחות, הכנת חלון תשלום, בירור Notify דרך דוח מאומת, והענקה אטומית חד־פעמית של קויינס או מנוי לתקופה. הגדרות החיבור כבויות כברירת מחדל; האדמין מציג בדיקת מוכנות ללא חשיפת סודות. עדיין נדרשים אימות פרטי המסוף ומיפוי הדוח מול הספק ובדיקת קצה־לקצה. חיובים מחזוריים והחזרים/ביטולים אוטומטיים אינם ממומשים. פירוט עדכני של המשתנים, נקודות הקצה והבדיקות מופיע ב־`TRANZILA_PREPARATION.he.md`.

**סדר עבודה מומלץ להשלמה:** לקבל את פרטי החשבון והחוזים החסרים → לממש מתאם והגדרות סודיות בשרת → חיבור תשלום מאוחסן → אימות הודעות והתאמת עסקאות → הענקה חד־פעמית ומנויים → החזרים ומסמכים → בדיקות קבלה → הפעלה מבוקרת. הגדרות סביבה חדשות צריכות להתחיל כבויות; שם משתנה מקומי אינו טענה שטרנזילה תומכת באותה אפשרות.
